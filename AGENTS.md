## 1. Project overview

AngkorFetch (`angkorfetch` on crates.io) is a fast, cross-platform system information
("fetch") CLI for Windows, macOS, and Linux. It reads OS data directly (Windows Registry
and CIM/WMI, Linux `/sys` and DMI, macOS `sysctl` and `system_profiler`) and prints it
next to an adaptive ASCII logo. Missing data degrades to `Unknown` or `N/A`; the program
never aborts on missing hardware or permissions.

Distribution matters as much as the code: the binary ships through GitHub Releases,
crates.io, quick-install scripts, and package manifests (Homebrew, WinGet, deb, rpm,
AUR, Flatpak, Snap). See [docs/PACKAGING.md](docs/PACKAGING.md) for the status of each.

## 3. Architecture and directory structure

```text
src/main.rs        Whole CLI: OS queries, parsing helpers, logo/colour rendering, main(), unit tests
scripts/           sync_package_manifests.py (+ unittest suite and testdata/ golden file)
Formula/           Homebrew formula, GENERATED by scripts/sync_package_manifests.py
winget-pkgs/       WinGet manifests, GENERATED by the same script after a release
linux/ flatpak/ snap/   Distro package specs and build helpers
get.sh get.ps1     Quick installers, served to users straight from the main branch
install.sh install.ps1  Local installers
.github/workflows/ release.yml (test, build, package, release), sync-packages.yml
docs/              Developer, maintainer, packaging, and release guides
team/              AI harness: roles, task records, command definitions
```

Inside `src/main.rs`:

- **I/O wrappers**: `run_stdout`, `run_powershell`, `reg_val` return `Option<String>` and swallow failures.
- **Pure parsers**: `parse_*` functions take strings, return values, and are unit-tested on every OS.
- **Collectors**: `get_*` functions combine I/O and parsers per OS with `cfg!(target_os = ...)` or `#[cfg(...)]`, and always return a printable `String`.
- **Rendering**: logo tiers (`LOGO_FULL`, `LOGO_COMPACT`), gradient and truecolor detection, `wrap_text`, `print_boxed`.
- **Tests**: `#[cfg(test)] mod tests` at the end of the file.

Full layout and per-OS data sources: [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).

## 6. Coding standards

- Idiomatic Rust; `cargo fmt` output is the formatting standard. Python follows PEP 8 and uses only the standard library.
- **No new crates or Python packages** without explicit maintainer approval.
- **No panics on system data.** `src/main.rs` currently has zero `.unwrap()` calls; keep it that way. Use `Option`, `.ok()`, `?` inside `Option`-returning helpers, and fall back to `"Unknown"` or `"N/A"`.
- **Platform parity**: a change for one OS must not alter behaviour on the others. Guard OS-specific code with `cfg`.
- Prefer native APIs or system files over spawning shells; when a subprocess is unavoidable, go through `run_stdout` / `run_powershell`.
- Keep parsing separate from I/O so it can be unit-tested on any host, and add a test for every new `parse_*` function.
- Stay focused: no unrelated refactors, renames, or reformatting of untouched code.

### Naming conventions

| Item | Convention | Example |
|---|---|---|
| Functions, variables | `snake_case` | `get_ram_details`, `term_width` |
| Data collectors | `get_<field>` | `get_battery` |
| Pure parsers | `parse_<thing>` | `parse_linux_battery` |
| Constants | `SCREAMING_SNAKE_CASE` | `LOGO_FULL` |
| Types | `PascalCase` (FFI structs keep the Win32 name) | `LogoTier`, `SYSTEM_POWER_STATUS` |
| Tests | `test_<function>` or a sentence | `test_parse_ports`, `tiers_step_down_with_available_width` |
| Branches | `feat/*`, `fix/*`, `chore/*`, `docs/*` | `fix/portability-audit` |
| Task files | `TASK-NNN-kebab-case.md` | `TASK-001-bootstrap-task-tracking.md` |

### Error handling

- Collectors return a printable `String`, never `Result` to `main`, and never print errors.
- Subprocess helpers discard stderr and return `None` on non-zero exit or empty output.
- Scripts in `scripts/` fail loudly with a non-zero exit code and a clear message; they must stay idempotent (identical bytes when already current).
- Installers keep `set -euo pipefail` (shell) and `$ErrorActionPreference = "Stop"` (PowerShell). The quick installers (`get.sh`, `get.ps1`) verify the SHA256 from `checksums.txt` and abort before installing on any download or checksum failure. `install.sh` and `install.ps1` build from source and fetch rustup without checksum verification.

## 7. Security requirements

- **Never** read, print, copy, or commit `.env` files, tokens, keys, credentials, or certificates. This includes the `PACKAGE_SYNC_TOKEN` repository secret.
- Never hand-edit SHA256 values in `Formula/` or `winget-pkgs/`. They come only from a release's `checksums.txt` through `scripts/sync_package_manifests.py`.
- `get.sh` and `get.ps1` are executed by users via `curl | bash` and `irm | iex` from `main`. Treat every change to them as security-sensitive: download only from `github.com/AMRSKH/angkorfetch` release URLs over HTTPS and keep checksum verification intact.
- Do not weaken CI gates (`test` with its fmt, Clippy, and test steps; `version-check`; formula `--check`) or workflow `permissions`.
- Documentation rules are not a security boundary. Respect the real permission settings of the tool you run in.

### Approval required (ask the maintainer first)

| Allowed without asking | Ask first |
|---|---|
| Reading non-sensitive files | Adding, removing, or upgrading dependencies |
| Running build, test, fmt, clippy, check commands | `git push` of any branch or tag |
| `git status`, `git diff`, `git log` | Creating or pushing release tags `v*` |
| Editing files inside the task's scope | Destructive Git: `reset --hard`, force push, history rewrite, branch deletion |
| Normal local commits for a completed task | Deleting important files or directories |
| | Changing CI workflows' triggers, permissions, or publishing steps |
| | Any external action: publishing packages, opening PRs, submitting to registries |

Approval already given for a specific action does not need to be requested again.

A **subset** of these rules is enforced by tool settings; the rest relies on these written
rules and each tool's own approval prompts:

- Claude Code (`.claude/settings.json`): the Read tool is denied `.env`, `.env.*`, `*.pem`,
  `*.key`. Both the Bash and PowerShell tools ask before `git push`, `git reset --hard`,
  `git clean`, `git branch -D`, `git rebase`, `git commit --amend`, `git tag`,
  `cargo add/remove/update/publish`, `pip`/`pip3`/`python -m pip install`, `gh pr create`,
  `gh pr merge`, `gh release`, `gh workflow run`. Edits under `.github/workflows/` ask first.
- OpenCode role subagents deny reads of `.env`, `.env.*`, `*.pem`, `*.key`.
- Not enforced: shell commands that read a secret file (for example `cat .env`), and
  command variants that do not start with the listed prefix (for example `git -C . push`).

## 8. Git workflow

- Branch model ([docs/MAINTAINING.md](docs/MAINTAINING.md)): `main` is production and the
  release source; `dev` is integration; `feat/*` and `fix/*` are short-lived topic
  branches; `automation/sync-packages-*` is created by CI. The harness also uses `chore/*`
  and `docs/*` for non-code work. Feature PRs target `dev`; urgent fixes and docs may
  target `main` ([CONTRIBUTING.md](CONTRIBUTING.md)).
- Do not edit directly on `main` or `dev`; start a topic branch first.
- Commit messages follow Conventional Commits and end with the Task ID:
  `type(scope): imperative summary [TASK-NNN]`. Types in use: `feat`, `fix`, `docs`,
  `chore`, `ci`, `refactor`, `test`. Trivial changes without a task file omit the Task ID.
- **One completed task, one work commit**, created immediately after the task passes
  validation and QA. No permission is needed for that local commit.
- After the work commit, record its hash in the task file and commit only that file as
  `chore(tasks): close TASK-NNN [TASK-NNN]` (a commit cannot contain its own hash).
- Before every commit: `git status`, review `git diff --cached`, stage files by path
  (never `git add -A` blindly), and confirm no secrets or unrelated changes are staged.
- If any required check fails, do not create a success commit.
- Never rewrite existing history to split old commits. Never push without approval.

### Pre-commit hook

`.githooks/pre-commit` (POSIX `sh`, no dependencies) aborts a commit when a check for the
staged files fails. Enable it once per clone:

```bash
git config core.hooksPath .githooks
```

| Staged paths | Checks run |
|---|---|
| `*.rs`, `Cargo.toml`, `Cargo.lock` (added, changed, or deleted) | `cargo fmt --check`, `cargo clippy --all-targets --all-features --locked -- -D warnings` |
| `scripts/`, `Formula/`, `winget-pkgs/` (added, changed, or deleted) | script unit tests, `sync_package_manifests.py --check` (Python found as `python3`, `python`, or `py -3`) |
| `*.sh` | `bash -n` on each staged script that still exists |

The hook checks the working tree, so unstaged edits to the same files are checked too.
It does not run `cargo test`; final validation does. Never bypass it with `--no-verify`
without maintainer approval. If it fails, fix the cause and commit again.

## 9. Task management

Every non-trivial change has a Task ID and one task file in `team/Tasks/`.
Rules, ID lookup, statuses, and the template: [team/Tasks/README.md](team/Tasks/README.md).

- Format: `TASK-NNN-short-description.md`, sequential from `001`, never reused or overwritten.
- Statuses: `Pending`, `In Progress`, `In Review`, `Blocked`, `Completed`.
- Update the task file as work progresses; it is the shared state between roles and tools.
- `Completed` only after validation passed, QA accepted, the work commit exists, and its hash is recorded.

### Team responsibilities

Work moves through four roles defined in [team/README.md](team/README.md):

| Role | Responsibility | Edits |
|---|---|---|
| [Advisor](team/Advisor/README.md) | Approach, risks, affected platforms, test plan | Task file only |
| [Dev](team/Dev/README.md) | Implementation and checks with real results | Code, tests, task file |
| [QA Review](team/QA-Review/README.md) | Independent verification, severity-ranked findings, verdict | Task file only |
| [Docs](team/Docs/README.md) | Documentation that matches verified behaviour | Docs, task file |

QA acceptance is required before a task commit. QA findings go back to Dev until
accepted or `Blocked`.

## 10. Definition of Done

A task is `Completed` only when every applicable item holds. If an item cannot be
checked, write the reason in the task file. Never fabricate results.

- [ ] Requirements understood; Task ID assigned; task file created
- [ ] Implementation complete, follows the conventions above, no unrelated changes
- [ ] `cargo fmt --check` passes
- [ ] `cargo clippy --all-targets --all-features -- -D warnings` passes
- [ ] Relevant tests pass (`cargo test --locked`, script tests, `--check`)
- [ ] Build succeeds when Rust code or `Cargo.*` changed
- [ ] QA Review completed and accepted; security considerations reviewed
- [ ] Documentation updated when behaviour, commands, or packaging changed
- [ ] `git diff` reviewed; separate local work commit created
- [ ] Commit hash recorded; status set to `Completed` in the close commit

## 11. Documentation requirements

- User-facing behaviour changes update `README.md`; developer workflow changes update `docs/DEVELOPMENT.md` or `CONTRIBUTING.md`; release or packaging changes update `docs/RELEASING.md` or `docs/PACKAGING.md`.
- Never mark a package or install method "Available" until it is published and verified. Use `[Pending]` or `[Planned]`.
- Never document unimplemented or unverified behaviour as working.
- New harness and task files start with the `Author` / `Date` / `Task` header. Exempt: source code, JSON, YAML, TOML, manifests, and files a tool parses from the first line (`AGENTS.md`, `CLAUDE.md`, and the command, agent, and skill wrappers whose first line must be `---` frontmatter).
- Keep docs concise; link instead of duplicating.
